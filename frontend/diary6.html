Q1 ; alert fatigue and designing minimal alerts

alert fatigue happens when a developer or system admin gets bombarded with so many constant, non-critical, or false alerts that they start ignoring them entirely. when everything is marked as urgent, nothing actually feels urgent.

a real-world example is an engineer getting spammed with 50 automated emails every night about tiny temporary cpu spikes, so when a critical database crash alert actually happens, they sleep through it because they muted the entire channel.

to avoid alert fatigue in a small student projects, we should only set up alerts for high-severity problems that require actual human action to fix, rather than logging every little status update. for example, instead of alerting when a single server request fails or when cpu hits 60% for five seconds, we should group and set thresholds: alert only if the entire app is returning 500 server errors for more than 5 minutes straight, or if the main database is completely unreachable. for a simple project stack running on something like docker or rahti, a minimal set of three alerts would be: a ping check that alerts if the frontend web server goes down completely, an error rate threshold that triggers if more than 5% of requests fail in a 10-minute window, and a storage warning if disk space hits 90%. keeping it to actionable, high-priority thresholds ensures we only get notified when our app actually needs immediate fixing.

Q2 ; liveness probe vs readiness probe in kubernetes/rahti

liveness and readiness probes are automated health checks used by kubernetes and rahti to keep containerized apps running properly. even though both check if a container is doing okay, they serve two very different purposes. a liveness probe checks if your app container is actually running or if it has frozen/deadlocked, while a readiness probe checks if your app is fully ready to accept incoming user traffic.

a simple example of the difference is when a web app first starts up: it might take 30 seconds to load database connections and cache files into memory. during those 30 seconds, the app is alive but not ready. the readiness probe stays negative so kubernetes doesn't route user web requests to a container that isn't ready to answer them yet. the biggest difference would be what happenes when they fail. if a liveness probe fails, kubernetes assumes the app is stuck forever and automatically kills and restarts the container. if a readiness probe fails, kubernetes doesn't kill the container; it just temporarily removes it from the service load balancer so no users hit it until it recovers and becomes ready again.

Q3 ; the three pillars of observability

observability is all about understanding what's happening inside a system based on the data it produces. each pillar gives a different perspective on system health.

metrics are numeric values aggregated over time that show overall performance trends. they are best suited to answer high-level operational questions like "what is our current server CPU usage and request error rate?" they give you quick dashboards and alerts when something starts performing poorly across the whole app.

logs are detailed text records of individual events that happened. they are best suited to answer specific event questions like "why did user #402 get a 500 server error at 10:15 am?" because you can look at the exact error message and stack trace printed by the code at that moment.

traces track a single request's journey as it passes through multiple microservices. they are best suited to answer distributed performance questions like "which specific database query or microservice API call is causing checkout requests to take 6 seconds?" because a trace breaks down the exact time spent at every step of that user's request path.

Q4 ; continuous integration vs continuous delivery vs continuous deployment

continuous integration (ci), continuous delivery, and continuous deployment are progressive stages in automated software releasing.

continuous integration focuses purely on code quality early on, like whenever developers push code updates to a shared repository like github, automated tools build the app and run tests to catch bugs before merging code together.

continuous delivery and continuous deployment take automation further into testing and production environments. every code change that passes ci tests is automatically built and packaged into a release artifact, then automatically deployed to a staging environment ready for production. however, deploying to live users still requires a manual button push or human approval from a team lead.

continuous deployment completely eliminates that manual human gate. every single code change that passes the automated pipeline is pushed directly to live production servers without human intervention. a company uses continuous delivery when they need business or compliance sign-offs before going live, whereas fast-moving teams use continuous deployment so bug fixes and small features hit live users within minutes of passing tests.

for this assignment, i set up an automated ci/cd pipeline using github actions to deploy my multi-container app to rahti, configured liveness/readiness probes to handle app health, and added basic logging to track requests. first i wrote a github actions workflow .github/workflows/deploy.yml that triggers on every push to the main branch. it logs into the rahti cluster using secret tokens stored safely in github repository secrets, builds the backend container image, pushes it to the registry, and updates new deployment rollout. to confirm that a commit actually triggers a real deployment on rahti, i checked the pod details in the rahti console right after pushing. the pod start time updated and a new pod instance was created with the updated image tag.

then, in my deployment config, i added a liveness probe and a readiness probe pointing to the /healthz endpoint on the backend service. to test that the cluster actually reacts to a failing probe, i intentionally broke the /healthz route in server.js by making it return an HTTP status code of 500 instead of 200 and pushed the change. as expected, rahti hit the /healthz endpoint, detected the consecutive 500 status codes, and marked the container as unhealthy. the pod dropped out of service endpoints and entered a CrashLoopBackOff state as kubernetes tried to restart it to recover.

the backend logs incoming HTTP requests (like probe checks to /healthz) directly to standard output. this allows us to track incoming traffic, monitor probe hits, and troubleshoot errors directly through the rahti pod log viewer or using terminal commands like oc logs.
